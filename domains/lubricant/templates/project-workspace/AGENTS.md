## 核心原则：免 @ 自动化调度（Zero-Friction Processing）
- **严禁要求用户手动记忆或在输入中 @ 技能名称**。用户只负责输入自然语言需求、工况背景、配方思路、测试数值或提问。
- **意图自动识别与静默调度**：一旦用户输入数据或发出指令，你必须自动识别所属研发阶段，自动在后台调度安装在 `~/.config/opencode/skills/` 的领域技能与检验脚本：
  1. **立项与性质定义**（新产品/优化/降本/定制/探索） -> 自动执行 `project-definition`，生成/更新 `project.json`。
  2. **工况环境与参数**（温度/载荷/转速/水分） -> 自动执行 `duty-definition` & `duty-challenge-analysis`，生成/更新 `duty.json` / `challenge.json`。
  3. **失效模式与关键指标**（胶合/微点蚀/轴承失效/CTQ） -> 自动执行 `failure-ctq-analysis`，生成/更新 `failure_ctq.json`。
  4. **测试方法评定与资格认证** -> 自动执行 `test-method-qualification`，生成/更新 `test_method.json`。
  5. **基础油体系/配方骨架/成本核算** -> 自动执行 `formulation-design`，生成/更新 `design_space.json`。
  6. **混兑实验设计** -> 自动执行 `doe-design`，生成/更新 `experiment_design.json`。
  7. **输入真实测试数据/实验室结果** -> 自动执行 `experiment-import`，生成/更新 `experiment.json`（严格要求物理真实，拒绝捏造）。
  8. **数据统计分析/回归拟合** -> 自动执行 `statistical-analysis`，生成/更新 `model.json`。
  9. **配方优化与边界求解** -> 自动执行 `optimization`，生成/更新 `optimization.json`。
  10. **阶段评审与决策门放行** -> 自动执行 `gate-review`，生成/更新 `gate.json`。
  11. **阶段流转合规** -> 每次阶段流转前自动读取并执行 `lubricant-rd-agent` 路由规则，严禁违规跳步。
  12. **活报告同步** -> 每次任意技能执行并落盘工件后，同步更新活报告（规则见下方"活报告维护"）。

## 数据自动结构化与落盘规则
- 用户输入任何参数或实验数据后，不仅在 `notes/` 与 `docs/` 记录人类可读文档，**必须同时自动生成合规的标准 JSON 工件（Artifact）**存入项目根目录或对应数据目录。
- 每次生成或更新数据，同步维护 `knowledge/current-state.md` 与当前测试矩阵状态。
- 遇到必填字段缺失时，向用户发起清晰简短的单轮提问（解释为何需要此项），严禁自行捏造物理实验数据。
- **MD 文件命名规则**：所有生成的 `.md` 文件名必须采用 `YYYY-MMDD-<标题> v<主.次>.md` 格式（如 `2026-0907-XX开发报告 v0.1.md`）；内容实质修订时主.次版本号至少 +0.1，文件名中的日期改为最后更新日期（旧版本由 git 历史追溯，不在工作区保留重复副本）。

## 活报告维护（Living Report）
- 唯一报告文件：`docs/<YYYY-MMDD>-<项目名>开发报告 v<主.次>.md`（由 `templates/project-workspace/docs/开发报告模板.md` 初始化并按上述命名规则命名），按论文/总结报告格式组织，作为随项目推进持续更新的"活报告"；每次更新报告后，同步更新本条中的"当前"文件名。
- 触发时机：每次技能执行产生工件落盘、阶段流转、门禁状态变化或新实验数据导入后，必须同步更新该报告，不得只更新 JSON 工件。
- 每次必同步的最小集合：
  1. 头部"最近更新"日期与一句话版本说明；
  2. 摘要中的进度描述（当前阶段与关键结论）；
  3. "结果与讨论"章节中的当前进度小节（工件链 n/11、当前阶段、下一步行动）；
  4. 附录 A 工件清单（新增工件及其状态）。
- 写作约束：只陈述已验证事实；推测或待验证内容必须显式标注"待验证"；不静默改写历史章节，新证据以增量方式修订并注明数据来源。
- 最终交付：项目全门禁通过（gate-review VERIFIED）后，对该报告做一次终稿校对（数据一致性、日期、引用），即为完整开发报告交付。

## 门禁签署记录（Gate History）
- **`gate.json` 只承载决议本身**：不得写入签署人、时间戳或自定义结果字段 —— `schemas/gate.schema.json` 设了 `unevaluatedProperties: false`，多余字段会被直接判非法（已实测 REJECT）。
- **签署人与时间戳另存追加式记录**：`docs/gate-history.jsonl`，每行一条 JSON，字段固定为
  `{"gate_id": "...", "gate_status": "GO|HOLD|PIVOT|KILL|FREEZE", "operator": "...", "signed_at": "<ISO 8601>", "note": "..."}`。
- **追加，不覆盖**：每次门禁决议落盘都新增一行，旧行原样保留。该文件是唯一可追溯"谁在何时签了什么"的地方。
- **`gate_id` 递增**：同项目已存在 `GATE-<project_id>-NNN` 时，新决议取 `NNN+1`；严禁复用编号覆盖历史决议。
- 该文件写失败**不影响** `gate.json` 已落盘的事实，但必须在回执中明确告知用户"签署记录未写入"。

## 输出与沟通风格
- 中文、极简、严谨，保留专业工程实质，符合行业专家水准。
- 处理完后直接告知用户：
  1. 识别并推进到的研发阶段；
  2. 自动完成结构化落盘的工件；
  3. 当前关键指标达标评估与下一步建议行动。
